## 4. Install-mechanism decision (argued)

**Chosen: external clone referenced by path, with the harness-visible surface reaching it via symlinks.**

Concretely: `spine/` (this repo, `/Users/michaelbart/spine`) is cloned once, standalone, not inside any project. In `horizon/`:
- `.claude/skills/<name>` → symlink to `spine/core/skills/<name>` (per-skill directory symlinks; confirmed supported).
- `.claude/agents/<name>.md` → symlink to `spine/core/agents/<name>.md` (confirmed supported empirically — see §2.2, undocumented but real).
- `.claude/rules/<name>.md` → symlink to `spine/core/rules/<name>.md` (confirmed supported).
- `.claude/hooks` → **directory-level** symlink to `spine/core/hooks` (this one isn't a Claude-Code-parsed directory the way skills/agents/rules are — it's just a path a shell command resolves — so a whole-directory symlink is simplest and was not separately tested, since it's an ordinary filesystem symlink with no Claude-Code-specific resolution logic involved).
- `.claude/settings.json` (committed, team-shared — to be created in Phase B/C) wires hooks as `${CLAUDE_PROJECT_DIR}/.claude/hooks/<name>`, which resolves through the symlink transparently (this exact pattern — `${CLAUDE_PROJECT_DIR}/.claude/hooks/...` — is what was used and confirmed working in the throwaway hook test, §2.1).
- `core/scripts/*` (the portable, harness-independent layer) are reached by skills via `${CLAUDE_SKILL_DIR}`-relative paths — since `${CLAUDE_SKILL_DIR}` resolves to the skill's *real* location (the symlink target inside `spine/core/skills/<name>/`), a skill body can reference e.g. `${CLAUDE_SKILL_DIR}/../../scripts/floor` and it resolves correctly without needing a second symlink for scripts.
- Project-owned files — `.spine/adapters/`, `.spine/capabilities.json`, `.spine/protected-paths.conf`, `CLAUDE.md`, `docs/`, `work/` — are real files living in `horizon/`, never symlinked, per the deliverable manifest's own distinction between core and project-owned files.

**Why this over copy or submodule:** copy-and-vendor and git submodule both turn *every* core update into a commit in the project's own history (a full re-copy diff, or a submodule-pointer bump) — exactly the cost the build prompt says to avoid if possible. The symlink approach means updating the core is `git pull` inside `spine/`, full stop — zero commits in `horizon/` after the one-time setup commit that creates the symlinks and `.claude/settings.json`. That one-time setup commit is unavoidable under any mechanism (the harness has to find *something* at those paths) and is cheap.

**Cost, stated honestly for the tradeoffs doc:** symlink targets are absolute paths tied to this machine's layout (`/Users/michaelbart/spine/...`). For a second engineer on a second machine, or CI, this breaks unless `spine/` is cloned to the identical path, or the install script is re-run to regenerate machine-local symlinks. Given Layer 1 confirmed **solo, single-stream** for this engineer, this is an acceptable v1 tradeoff — but it is a real limitation, not a wash, and will be stated plainly in `docs/tradeoffs.md` in Phase D, with "team use needs either a fixed clone-path convention or a switch to submodule/copy" as the noted mitigation path.

**Verified, not assumed:** the symlink resolution for skills (per docs) and agents (empirically, §2.2) and rules (per docs) is real on Claude Code 2.1.224. The hook path-substitution pattern is real (§2.1). Nothing about this mechanism is speculative.
